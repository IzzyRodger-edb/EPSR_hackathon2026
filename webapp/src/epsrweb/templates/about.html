About: what this does, and the theory behind it

The problem

A diffraction measurement on a liquid or a glass does not give you a structure. It gives you one curve per sample: the differential scattering cross section F(Q), which is a weighted sum of all the partial structure factors of the material. For water there are three partials (O–O, O–H, H–H) behind every single measured curve, so one measurement cannot be inverted — the problem is underdetermined.

Two things make it tractable. First, isotopic substitution: hydrogen and deuterium scatter neutrons quite differently, so H2O, D2O and an HDO mixture weight the same three partials in three different ways. Measure all three and the problem becomes well determined. Second, a model: an atomistic configuration is guaranteed to be physically possible — atoms do not overlap, molecules keep their geometry — which is a constraint no direct inversion of the data can impose.

Empirical Potential Structure Refinement

EPSR, due to A. K. Soper, is how those two ideas are combined. A Monte Carlo simulation of a periodic box of molecules runs on a reference potential — Lennard-Jones plus Coulomb, a standard force field. That alone gives a plausible liquid, but not one that agrees with your data.

So after every few cycles the simulated F(Q) is computed for each of your samples and compared with the measurement. The difference, in Q space, is fed back as a correction to an empirical potential (EP): one extra pair potential per atom pair, refined iteratively, that nudges the simulation towards the data. Its amplitude is capped by a parameter called ereq, which is what stops the refinement from inventing whatever potential reproduces the noise.

The result is a set of atomic configurations consistent both with a sensible force field and with every measured data set at once. From them come the partial pair distribution functions g(r) — and from those, the quantities people actually quote: peak positions, coordination numbers, hydrogen-bond counts, bond-angle distributions, tetrahedral order.

How to tell whether it worked

  • The R-factor plateaus. It is the mean squared difference between data and simulation over the fitted Q range. For a liquid against good neutron data it falls to a few times 10-4.
  • The EP amplitude settles below ereq. Still rising means the refinement has not finished. Pinned at ereq means the fit is being limited by the cap, and a large EP next to the reference potential means the reference potential was poor.
  • The structural numbers stop moving. First-peak positions and coordination numbers that are still drifting are not results yet.
  • The pressure is plausible — a few kbar for a liquid at its measured density.

Residual misfit is not always failure. In hydrogenous samples the region below Q ≈ 2 A-1 is dominated by inelasticity effects that EPSR does not model, and it is normal for the fit to be worst there.

What this software is

The engine is a Rust translation of the Fortran EPSR suite, verified byte for byte against the original on its test case and on three real systems: water on SANDALS, amorphous silica and the Cu-BTC framework on NIMROD. Around it:

epsr
the Python interface to the Rust engine.
epsrvis
the analysis and plotting toolkit. It records a refinement iteration by iteration, which is what makes the convergence and residual-map figures possible: EPSR itself only writes its result files after the last iteration of each call, and overwrites them each time.
Mellor
the agent. It inspects your data, proposes a model system as JSON, generates the EPSR input files and a standalone Python script, runs the engine, analyses the result and writes the discussion.
this web app
accounts, uploads, the job queue, the seaborn figures drawn from the run's CSV tables, and the Overleaf publishing step.

What the language model does and does not do

The model only produces the specification of the model system and the prose. It never runs the simulation, never computes a number, and cannot execute shell commands or read anything outside the folder of your run. Every figure and every number on a results page comes from the engine.

That boundary is why each run folder contains run_<name>.py: a standalone script, with the input files embedded, that reproduces the refinement using only the open-source wrapper and toolkit — no model involved. If you doubt a result, run that.

A model system outside the validated library is the model's proposal, and is marked unvalidated in the report. Its force-field parameters are then yours to check.

Completing the installation

This app runs with or without the refinement stack. Without it you get the interface, the upload validation and the Overleaf path, and every results page is stamped as a demonstration. Three packages have to be importable by the server process: 

pip install -e ./python                                  # epsr: the engine (compiles Rust)
pip install -e ./visualisation/python_visualisation_toolkit   # epsrvis: analysis and plots
pip install -e ./mellor                                  # the agent itself
pip install -e ./mellor --no-deps                        # ... or without re-resolving

The first one is the one that fails. It builds a Rust extension through maturin, which targets the same ABI as your Python interpreter: on Windows that means the MSVC toolchain, so you need Visual Studio Build Tools with “Desktop development with C++” and rustup default stable-x86_64-pc-windows-msvc. A GNU-only Rust toolchain cannot link it. On Linux and macOS a stock Rust install and a C compiler are enough.

Restart the server afterwards; /healthz reports mellor=yes when it worked, and the banner at the top of this page disappears. Keep the repository checkout intact: Mellor resolves ../python and ../visualisation/python_visualisation_toolkit relative to its own folder.

For the local language-model backend add pip install -e "./mellor[local]", which pulls in torch; for the hosted backend set a Hugging Face token in Settings. Neither is needed for the “no language model” option, which refines against a validated system.
